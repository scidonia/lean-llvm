# The JSON route's stage timings

The route artifact answers one document per invocation: it decides the document
with the library's `admission`, stages it in the record's shape, calls the
native object through the adapter, and prints the observation, the arena and the
event stream.  This page records where its time goes, measured stage by stage,
beside the numbers for the object's optimisation level, the fallback's price,
and one external reference.  The outcome stage — 92–93% of the route — is
dissected into its five parts, and set against a consumer that reads the same
result without printing, because the printed path's cost and a production
consumer's cost are not the same number.

Every time on this page is nanoseconds, every row is a median, and each row's
construction is stated with it.  Nothing here is compared against
[`kernel/json/measured/`](../kernel/json/measured/PROVENANCE.md): that
record's ratios came from a scratch tree, a different pipeline build and a
rotation this page does not share, so the only comparison is the reference arm
measured in the same session as the route, paired round by round.

## Reproducing it

```bash
bash probes/json/route/bench.sh 21
```

The script builds the route four times (two optimisation levels, each with and
without the stage instrument), generates its corpus, runs the stage rows, the
consumer rows, the process-wall rows, the paired measurements and the reference
arm, and prints the record below.  It re-executes itself inside
`systemd-run --user --scope -p MemoryMax=6G -p MemorySwapMax=1G`, so every
compile and every run is inside that cap whether or not the caller did it; the
cap it actually has is read back from the cgroup and printed.  `BENCH_CPU`
selects the CPU the arms are pinned to, `BENCH_ROUNDS` and `BENCH_PAIR_REPS`
size the paired sections, `BENCH_DIR` keeps the builds and the corpus, and
`SIMDJSON_SRC` names a simdjson source tree.  The corpus is generated by the
script from the commands it prints, so no input file has to exist beforehand.

The route's own interfaces for this are `--stages <file> <reps>`: one process,
`reps` repetitions, the document re-read inside every repetition, one median per
stage and per outcome part; and `--consume <file> <reps>`: the same fast path,
with the result read and never printed, priced as two readings.  Both are
documented in `probes/json/route/README.md` beside the build knobs `OPT` (the
kernel object's level) and `TIMING=1` (the adapter's stage instrument).

## What each stage contains

| stage | the work inside the timed region |
|---|---|
| `read_ns` | `IO.FS.readBinFile` of the document — reported apart from the stages, in no stage |
| `admission_ns` | the library's `admission`: the empty and length clauses, the opener count (`doc.data.toList.countP`), and the per-quote policy scan (`List.range doc.size` with the reference's scanner at each quote) |
| `staging_ns` | the record's shape in bytes: the window `[0,0,0] ++ doc ++ padding ++ 32`, and the four growing buffers zero-filled at the record's capacities, all as fresh `ByteArray`s |
| `copyin_ns` | the adapter's precondition checks and its copy of every caller buffer into its own allocation (14 `malloc` + `memcpy`) |
| `native_ns` | the call to `leanllvm_json_pipeline` alone |
| `copyout_ns` | the cursor reads and checks, the result `ByteArray` built from the header and both payloads, and the staging copies freed |
| `outcome_ns` | the tagged result decoded, the length consistency check, and the observation, arena and events printed as hex; the per-repetition sum of the five parts below |
| `outcome_decode_ns` | the tag, the length consistency check and the seven header words, read by `be64` |
| `outcome_slice_ns` | the arena and the events cut out of the result |
| `outcome_header_ns` | the observation line, built and written |
| `outcome_arena_ns` | the arena line, built and written as lowercase hex |
| `outcome_events_ns` | the events line, built and written as lowercase hex |
| `hex_arena_ns`, `hex_events_ns` | instrument-only: the same two lines rebuilt with the write removed, after the stage's timed window, so each printed line's write is the difference between its part and its hex figure |
| `total_ns` | admission's start to the end of outcome handling; the file read is outside it |
| `adapter_wall_ns` | the interval the caller saw around the adapter; `copyin + native + copyout` less it is the precondition checks and the adapter's own clock reads |

The copy cost is a visible line item: `copyin_ns` and `copyout_ns` are their own
columns, and the staging the caller pays before them is a third.  The adapter's
three intervals come from the instrumented build, which takes four clock reads —
one at copy-in's start, one at each of the two stage boundaries, and one at
copy-out's end — so the reads that bound an interval have their cost inside it.

The outcome parts come from the same mode, which calls the functions
`interpret` calls with a clock read between them, in `interpret`'s order.  The
two `hex_*` figures run after the stage's last clock read, so they are reported
but are not in `outcome_ns` or in `total_ns`.

## The consumer rows

`--consume` runs the fast path and reads the result the way a consumer that
keeps no printed copy would: the header words through `ByteArray` indexing, and
the event stream record by record at the widths `kernel/json/stage2.h`
documents (a tag for `{`, `}`, `[`, `]`, `true`, `false` and `null`; a tag and
eight bytes for a number; a tag, four length bytes and eight span bytes for a key
or a string).  Two readings are priced in the same repetition, alternating which
goes first: `consume_fold_ns` reads each record's tag, length and payload and
folds them with the arena's bytes into a checksum, and `consume_values_ns` does
the same while materialising one `Event` record per token and folding the
array, which is where a per-token allocation lands.  Nothing is printed per
repetition.  The mode exits 5 unless both readings count the same tokens, land
exactly on the event stream's end, and produce the same checksum; `check.sh`
pins a five-event fixture's counts as well.

## Reading it

**The route's own reporting dominates it.**  `outcome_ns` is 92.62–93.65% of
`total_ns` on the three scalar arrays, 91.0% on the depth-128 document and 79.2%
on the escape-heavy one.  Inside that stage, however, the cost is not the two
payloads' hex: it is the header reader.

| document | decode | slice | events | arena | header | outcome | decode % | events % |
|---|---|---|---|---|---|---|---|---|
| `fast-nums-4096` | 1,859,400 | 67,254 | 269,345 | 173 | 605 | 2,206,408 | 84.27 | 12.21 |
| `fast-nums-16384` | 7,571,515 | 259,347 | 1,093,491 | 574 | 1,360 | 8,934,072 | 84.75 | 12.24 |
| `fast-nums-65536` | 31,255,056 | 1,097,010 | 4,672,215 | 1,332 | 2,900 | 37,072,013 | 84.31 | 12.60 |
| `fast-esc` | 312,760 | 16,894 | 1,021 | 41,582 | 606 | 372,811 | 83.89 | 0.27 |

Unit: ns, medians of 21 repetitions from the same `--stages` row; the percent
columns divide a part's median by that row's `outcome_ns` median.  Construction:
`outcome_ns` is the per-repetition sum of the five parts, so the five clock
reads that divide them are inside the stage and nothing else is; the parts are
medians of per-repetition sums, so their percentages need not add to exactly
100.  `arena` is 0.01% on the scalar arrays because their arena is empty, and
11.2% on the escape document, whose arena carries the unescaped bytes.

**The header decode is fifty-six list materialisations.**  `be64` reads one
byte as `(bs.toList.getD (i + k) 0)`: the whole result's list is built, then
walked from its head to the index.  Each header word is eight such reads, and an
observation needs seven words, so one outcome stage costs 56 materialisations of
`80 + ndst + nev` bytes and 56 head-to-index walks on top.  At 6,229 result
bytes that is 348,824 cons cells for 1,859,400 ns — 33,204 ns per
materialisation, 5.3 ns per cell — and 5.7 ns per cell at 98,389
result bytes, where one materialisation is 558,126 ns.  The accounting is in the
artifact rather than inferred: the emitted `l_be64___lam__0` calls
`l_ByteArray_toList` once per byte read, and `decodeResult` calls `be64` seven
times.  This is the instrument's own conversion, not a decoder for the
pipeline's result: the consumer below reads the same header and walks the whole
event stream in 8,321 ns.

**The printing cost is the hex conversion, not the write.**  The events line is
269,345 ns at 4 KiB and its build-only figure is 263,002 ns, so 98% of the line
is building the string and 6,343 ns is writing it; at 64 KiB the split is
4,672,215 against 4,467,232 ns, so 204,983 ns of the 4.7 ms is the write of
196,631 characters.  Building it is `hex`'s shape: `toList`, one `String` per
byte through `Nat.toDigits 16`, then `join`.  Per event-stream byte that is
42.77–45.44 ns on the scalar arrays and 60.9 ns on the escape document;
`hex_arena_ns` prices the escape document's 1,000 arena bytes at 39,599 ns,
39.6 ns per arena byte.

**The slicing is the third cost.**  Two `toList` materialisations cut the
payloads out: 67,254 ns at 6,229 result bytes (3.05% of the stage) and
1,097,010 ns at 98,389 (2.96%).  The observation line is 605 ns and the empty
arena's line 173 ns; neither is a lever.

**What a consumer pays.**  A consumer that reads the same result and keeps
values pays two to three orders of magnitude less than the printed path:

| document | tokens | fold | values | fold/event | values/event | fold/byte | values/byte |
|---|---|---|---|---|---|---|---|
| `fast-nums-4096` | 685 | 8,321 | 12,018 | 12.15 | 17.54 | 1.35 | 1.95 |
| `fast-nums-16384` | 2,733 | 32,851 | 47,897 | 12.02 | 17.53 | 1.34 | 1.95 |
| `fast-nums-65536` | 10,925 | 143,984 | 215,337 | 13.18 | 19.71 | 1.46 | 2.19 |
| `fast-esc` | 3 | 1,816 | 1,859 | 605.33 | 619.67 | 1.79 | 1.83 |

Unit: `fold` and `values` are ns per document (medians of 21 repetitions, the
alternating order above); the `/event` columns divide each median by the token
count and the `/byte` columns by `ndst + nev`, both from the same consumer row.
`tokens` is the number of event records, so the escape document's three events
over 1,015 payload bytes make its per-event figures meaningless and its per-byte
figures the ones to read.

The printed path's cost over the same token and byte counts is 3,221–3,393 ns
per event and 42.77–45.44 ns per event-stream byte on the scalar arrays, and
124,270 ns per event on the escape document.  Dividing the two per-document
medians, the printed stage is 183.6, 186.5, 172.2 and 200.5 times the consumer's
values reading on the four documents (unit: multiplier of ns medians, the
same document and session; the printed figure is the `TIMING=1` build's and the
consumer's the production build's, and the consumer's own code holds no clock
read).

**So the 2.4 ms is instrumentation.**  In this session the 4 KiB document's
outcome stage is 2.21 ms, and 84.27% of it is a header reader that rebuilds the
result's list for every byte it reads, 12.21% is the events line's hex
conversion, and 3.05% is cutting the payloads out.  A consumer that reads the
result and keeps values pays 12,018 ns on the same document — 18 ns per event
and 1.95 ns per payload byte — and 215,337 ns at 64 KiB, without per-token values
12–13 ns per event.  The honest production cost of reading this pipeline's
result at these sizes is therefore tens of nanoseconds per token, not
microseconds, and it is not the parser's cost either way: the object is
0.28–0.57% of the route's total.  The fixes are a follow-up and they are all on
the probe side — read the header by index (the consumer's `decodeIndexed` is the
measured shape), build the hex without a list and a `String` per byte, and cut
the payloads without materialising the result.

**The copy is cheap; the staging before it is not.**  For `fast-nums-65536` the
adapter copies 1,508,377 bytes (window 65,635; entry 262,436; escape 262,432;
arena 65,603; events 852,135; the nine fixed slots, 136) in 92,322 ns — about
16.3 GB/s.  The caller's staging of the *same* bytes costs 1,166,005 ns, about
1.3 GB/s: the `zeros` arrays are built element by element, so the stage that
exists to hand the adapter zeros is 12.6 times more expensive per byte than the
adapter's copy of them.  Both are small against the reporting, and the copy-in
figure is the one a caller could not remove (it is the FFI boundary); the
staging figure is allocator-plus-fill work the route chooses to do per call.

**Admission scans at 21.7–24.0 ns per input byte** on the three scalar arrays
and 31.9 on the escape-heavy one, and it is two scalar Lean passes over the
document: the opener count materialises `doc.data.toList`, and the policy check
materialises `List.range doc.size`, comparing each byte and running the
reference's body scanner at every quote.  At 65,539 bytes it is 1,572,790 ns
against the native call's 118,274 ns: the decision costs about thirteen times
the parse it admits.  This is a property of the domain's current decision
procedure as the library states it, measured through the route, not a property
of the object.

**The object against the reference.**  `native/parse` is 1.28–1.35 on the three
scalar-array documents and 0.52 on the escape-heavy one:

| document | `native/parse` med (min–max) | `core/pad+parse` med (min–max) |
|---|---|---|
| `fast-nums-4096` | 1.283 (1.215–1.393) | 41.3 (27.7–61.0) |
| `fast-nums-16384` | 1.293 (1.106–1.356) | 34.7 (31.1–44.9) |
| `fast-nums-65536` | 1.354 (1.147–1.447) | 38.1 (30.7–51.8) |
| `fast-esc` | 0.516 (0.490–0.537) | 19.7 (17.4–32.6) |

Unit: ratio of ns medians per document, both arms medians over the same
document in the same round, alternating which arm goes first.  Construction:
`native/parse` divides the route's `native_ns` by simdjson's `iterate` plus the
full value traversal (every string fetched, every key unescaped, every number
converted); `core/pad+parse` divides the route's `total_ns` less `outcome_ns`

per arm, no repeated work in either.  The escape-heavy document is the one shape
where the reference's traversal, which unescapes a 1,000-escape string, exceeds
the route's native stage.  The whole route over `pad+parse` is 91–483× and is
not tabulated: that ratio is the reporting, already a column above.

**The optimisation level is not a performance lever here.**  The object is the
six kernel translation units; `OPT` changes that level and nothing else, and the
two builds are measured in the same rounds, alternating order, with a third run
of the −O2 build in each round as the drift control:

| document | −O3/−O2 `native_ns` med (min–max) | −O3/−O2 `total_ns` med (min–max) | control: −O2/−O2 `native_ns` med (min–max) |
|---|---|---|---|
| `fast-nums-4096` | 1.008 (0.960–1.076) | 0.983 (0.968–1.039) | 0.990 (0.953–1.058) |

each round runs both builds on the same document with 5 repetitions each, and a

That is the performance number the flag gap

the route's object is a −O2 compilation where the proofs' body is a −O3
emission.  For the route's use of the object, at 2 KiB to 64 KiB, the
difference between the two levels is not distinguishable from this machine's
run-to-run drift.  The level changes which bodies the compiler inlines — the
correspondence page measures that — but not the route's cost at these sizes,
where the object is a fraction of a percent of the total (0.28–0.57%).

**The fallback's price is negative.**  `depth-129` is the document one bracket
pair past the domain, and the fallback answers it end to end in 8,251 ns, against
123,458 ns for the admitted `depth-128`; the 4,096-byte opener-rich
`scale-4096.json` is answered by the fallback in 435,820 ns against 2,355,937 ns
for the admitted 4,099-byte scalar array.  Unit: ns per document, medians of 21
repetitions of the whole route, the two documents of each pair differing by one
bracket pair (first pair) or in shape (second pair).  The reason is in the
columns above: the fallback's residual is the reference parse
(5,216 ns at 258 bytes, 201,901 ns at 4 KiB) plus one printed line, while the
fast path pays staging and hex printing of its payloads.  The floor the fast path
sits on is its own reporting; the residue is cheaper than that floor at these
sizes.  This is where an optimisation would pay: the stage table's dominant
column is not the parser.

## The instrument, and the two defects it has caught

The adapter's three intervals are recorded only under `ROUTE_TIMING`, and the
read is an `IO` action.  Both properties are load-bearing:

* **The gate is checked, not assumed.**  `build.sh` asserts with `nm` that
  `clock_gettime` is absent from the ordinary adapter's undefined symbols and
  present in the instrumented one, and the four builds in the record above each
  passed it.  An uninstrumented build's `--stages` refuses rather than printing
  zeros: the slots start at `UINT64_MAX` and the mode exits 6 with "no stage was
  recorded".
* **The first form of the getter was wrong, and the wrongness was visible.**
  Written as a pure extern with a literal index, `stageNsAt 0` was folded into a
  lazily initialised static, so every repetition reported the *first*
  repetition's intervals: copy-in appeared as 588 µs against a 230 µs adapter
  wall, a contradiction that cannot hold.  The fix is the `IO` return type and
  `lean_io_result_mk_ok`, which also makes the reads sequenced against the
  adapter call; the route's call is an `IO` action for the same reason.  A slot
  read that could move relative to the call would report the previous call's
  interval, and nothing in the row would look wrong.
* **The outcome parts are Lean-side reads on the same instrument.**  The five
  intervals are `IO.monoNanosNow` calls between the calls `interpret` makes, and
  `--stages` reports their per-repetition sum as `outcome_ns`; the hex-only
  probe runs after the stage's last read so it cannot enter `total_ns`.  The
  dissection then found the second defect: `be64`, a header reader written as
  "the result's byte at an offset", materialises the result's list per byte and
  was 83.9–84.7% of the stage it was measuring.  It looked like decoding the
  result and was the probe's own conversion, which is why the consumer mode
  reads the same header by index and why the fix, not the number, is the
  follow-up.

## What this does and does not establish

It establishes, for one session on this machine, the per-stage cost of the
route as it stands, the outcome stage's split across its five parts, the price
of a consumer that reads the same result without printing, the price of the
object's two optimisation levels against each other with a drift control, two
fallback documents' end-to-end cost beside the admitted document each is paired
with, and one paired comparison against simdjson 4.6.11.

It does not establish a portable number.  The host is shared, nothing is
isolated beyond a CPU pin, and the same-build control spread reaches 0.949–1.094
on `native_ns`: absolute medians from another session will differ by up to that
much, which is why the pair and the reference rows are ratios taken round by
round rather than differences of two runs.  The reference arm is two binaries,
not one process, so its alternation cancels drift but not the difference between
two address spaces; a single-process arm would need simdjson linked into the
route executable.

The consumer number is a floor, not every consumer's cost.  It walks the event
records and reads the arena's bytes, and it materialises one record per token
in the values reading; it does not rebuild strings from the spans, so a
consumer's per-string allocation sits above it, and rebuilding the hex is what
the printed path's column prices.  Its own correctness is asserted rather than
assumed: both readings must count the same tokens, land exactly on the event
stream's end, and produce the same checksum, the mode exits 5 otherwise, and
`check.sh` pins a five-event fixture's token count, arena length and event
length.  The printed/consumed multiplier divides a `TIMING=1` median by a
production median of the same document in the same session; the consumer's code
contains no clock read, so only the printed side carries the instrument.

And no row here says anything about the object's relation to the proved body —
that is [the correspondence page](json-route-artifact-correspondence.md)'s
record, and its residual is unchanged by any timing.
