# IR inventory — JSON structural recogniser

Spike for J0's "inventory the actual emitted IR before committing to a
semantics subset". Source and commands are reproducible; the scratch lives
outside the repository (`/tmp/jsonscan-spike`).

## What was compiled

A 32-byte block recogniser: load 32 bytes, compare against `" \ : , { } [ ]`,
OR the lane masks, extract one bit per lane.

* **Variant A** — explicit `_mm256_*` intrinsics (`cmpeq_epi8`, `or_si256`,
  `loadu_si256`, `movemask_epi8`).
* **Variant B** — a portable loop with no intrinsics, left to the vectoriser.

```
clang -O2 -mavx2 -S -emit-llvm scan.c -o scan_O2.ll      # 173 lines
clang -O0 -mavx2 -S -emit-llvm scan.c -o scan_O0.ll      # 1731 lines
```

**Update (2026-11-03) — the fragment list below was measured stale.** J2's
classifier is emitted from `probes/install/json/classify.candidate.c`, which
compares against the four whitespace bytes as well as the eight structural
bytes. Re-emitting that source at `-O2 -mavx2` shows that instcombine folds the
`'\t'` and `'\n'` comparisons into a range test, so the emitted instruction set
is not the source's and is not the structural-only kernel recorded in Variant A.
The measured fragment, and the command that regenerates it, are in
"Consequences" item 2. The Variant A and B sections are kept as the J0 findings
they were; the numbers that described the *required* fragment have been
corrected in place rather than contradicted.

## Variant A (intrinsics) — emitted body, verbatim shape

```llvm
%11 = load <32 x i8>, ptr %10, align 1
%12 = icmp eq <32 x i8> %11, splat (i8 34)      ; ×8, one per structural byte
%14 = or <32 x i1> %12, %13                     ; ×7
%27 = bitcast <32 x i1> %26 to i32              ; the mask extraction
%28 = or i32 %8, %27
%29 = add i64 %7, 32
%30 = icmp ugt i64 %29, %1
```

**No target intrinsics.** `_mm256_movemask_epi8` lowered to a **bitcast of
`<32 x i1>` to `i32`**, and every `_mm256_cmpeq_epi8`/`_mm256_or_si256`
lowered to portable vector `icmp`/`or`. The whole body uses:

|Construct|Count|
|---|---|
|`load <32 x i8>` with `align 1`|1|
|`icmp eq <32 x i8>`, splat operand|8|
|`or <32 x i1>`|7|
|`bitcast <32 x i1> to i32`|1|
|scalar `or`/`add`/`icmp`/`phi`/`br`/`getelementptr`|the rest|

Vector types seen: `<32 x i8>`, `<32 x i1>`.

This table is the **structural-only** kernel (eight bytes, eight `icmp eq`,
seven `or`). The twelve-byte classifier J2 captures has ten `icmp eq`, one
`icmp ult` and ten `or`; its measured counts are in "Consequences" item 2.

## Variant B (portable, auto-vectorised) — what the vectoriser chose

```llvm
%23 = load <8 x i8>, ptr %22, align 1
%24 = icmp eq <8 x i8> %23, splat (i8 123)
%28 = and <8 x i8> %23, splat (i8 -33)          ; case folding
%32 = icmp ult <8 x i8> %31, splat (i8 2)
%37 = shl nuw <8 x i32> splat (i32 1), %21
%38 = select <8 x i1> %36, <8 x i32> %37, <8 x i32> zeroinitializer
%44 = tail call i32 @llvm.vector.reduce.or.v8i32(<8 x i32> %39)
```

Vector types: `<8 x i8>`, `<8 x i1>`, `<8 x i32>`. Intrinsics:
`llvm.vector.reduce.or.v8i32`, `llvm.umax.i64`, `llvm.umin.i64`. A scalar tail
load handles the remainder.

## Consequences

1. **The recogniser needs no AVX2 intrinsic, and no shuffle.** Target-specific
   code is confined to the backend, which the programme already trusts, so the
   "AVX2" backend choice affects performance and the trusted compiler, not the
   semantics.
2. **The minimal vector fragment, regenerated from the captured artifact.** The
   earlier list here — a vector `load`/`store`, lane-wise `or`/`and`,
   `bitcast`, and `shl`/`lshr`/`trunc`/`select` — was measured stale on
   2026-11-03. The classifier's captured body contains no `store`, `and`,
   `shl`, `lshr`, `trunc` or `select`, and it does contain two instructions the
   earlier list did not name: `add <32 x i8>` and `icmp ult <32 x i8>`. The
   artifact is `probes/install/ir/json-classify.candidate.ll`, regenerated by

   ```bash
   nix develop -c bash probes/install/ir/capture-json.sh
   nix develop -c opt -passes=verify -disable-output probes/install/ir/json-classify.candidate.ll
   ```

   from `probes/install/json/classify.candidate.c`, at the optimizer form
   **clang 21.1.8, `-O2 -mavx2`, `x86_64-unknown-linux-gnu`**. Instcombine
   folds the `'\t'`/`'\n'` comparisons into a range test, which is where
   `add <32 x i8> … splat (i8 -9)` and `icmp ult <32 x i8> … splat (i8 2)` come
   from; at `-O0` the same source emits an `icmp eq` for each of the twelve
   bytes and neither of those two. The capture script prints the inventory it
   measured, refuses the constructs in its stop condition, and asserts these
   counts. The fragment the artifact requires, and nothing else:

   |Construct, as written in the captured block|Occurrences|
   |---|---|
   |`<32 x i8>`|13|
   |`<32 x i1>`|11|
   |`splat (i8 ` — includes the negative `splat (i8 -9)`|12|
   |`load <32 x i8>` (the parser models no load alignment; the emission's `align 1` is stripped, and under LLVM's own reading the bare load assumes `align 32`, so this fixture is parsed rather than compiled)|1|
   |`icmp eq <32 x i8>`|10|
   |`icmp ult <32 x i8>`|1|
   |`add <32 x i8>`|1|
   |`or <32 x i1>`|10|
   |`bitcast <32 x i1>` … `to i32`, on one line|1|
   |`ret i32`|1|

   Each row is checked by grepping the fixture's captured block for exactly
   that text — the counts are counted on the `define` block, not on the
   provenance comment above it — and the script fails if a count moves. The
   `bitcast` row asserts both tokens on the same instruction, so the result
   type is part of the claim rather than inferred from adjacency. Nothing else
   is in the body: no `store`, `and`, `shl`, `lshr`, `trunc`, `select`,
   `alloca`, `fence`, `extractelement`, `phi`, `getelementptr`, `call`,
   `shufflevector`, `insertelement`, `zeroinitializer` or
   `llvm.vector.reduce.*`.
3. **Cross-byte logic can stay scalar.** String state is a prefix-XOR over the
   32-bit quote mask (`x ^= x<<1; x ^= x<<2; x ^= x<<4; x ^= x<<8; x ^= x<<16`),
   and structural parity is a prefix-sum on the mask, both on `i32`/`i64` with
   the ordinary scalar model. That keeps the vector fragment confined to
   classification, which is the part SIMD is actually for.
4. **The model carries this fragment and the closed set around it.** Every
   construct the classifier's body uses is modelled and exercised by a proof;
   item 2's table is the measured list. The set is a little wider than the
   body: the five lane-wise integer binops `or`, `and`, `xor`, `add` and `sub`
   are admitted (`Parser.lean`, `parseBinop`'s vector arm, evaluated per lane in
   `Semantics.lean`, `evalInstr`'s `binopVec` case), of which the body uses `or` and `add`, and vector
   `icmp` is confined to `eq` and `ult` (`parseValueInstr`'s vector `icmp` arm). `Ty.vec` is
   `LeanLLVM/Basic.lean:19`, with
   `<32 x i8>` and `<32 x i1>` distinct types. A splat constant is
   `Const.splat` (`Basic.lean:44`): integer lanes only, so a non-integer splat
   has no representation and no printed form. The vector `load` is
   `Instr.load` (`LeanLLVM/Syntax.lean`) — the same constructor as the
   scalar load, and it carries no alignment field, which is why the captured
   `align 1` does not survive the round trip. The lane-wise forms are
   `Instr.icmpVec`, `Instr.binopVec` and `Instr.bitcastMask` (`Syntax.lean`),
   evaluated in `evalInstr` (`LeanLLVM/Semantics.lean`) and packed by
   `lanesToNat`, whose bit-level reading is `lanesToNat_testBit`. `LeanLLVM/JSON/ScanBlock.lean` proves the packed mask is the
   scalar transition's (`maskOfList_getLsbD`, `:219`), and
   `LeanLLVM/Vellum/JsonClassifyIR.lean` proves the emitted body returns that
   mask on every readable block (`scannerLLVM_refines`, `:838`), so the
   fragment is modelled *and* checked against a body that uses it.

   The forms **admitted since this inventory was written** — the ones the
   stage-1 classification-mask kernel is emitted with — are: `shufflevector` with
   a defined mask whose entries name a lane below `2n` (`Instr.shuffleVec`), a
   vector `load` at integer lanes whose total width is a whole number of bytes
   (`<4 x i64>`), a mask-only vector `store` (`store <n x i1>` whose total width
   is a whole number of bytes), a non-mask vector `bitcast` at equal total
   width (`Instr.vecBitcast`, `<4 x i64>` read as `<32 x i8>`), and vector
   `lshr` (`Instr.binopVec`, the per-sixteen-bit-lane shift the high-nibble
   extraction uses).  Vector `shl` is admitted as the same operation in the other
   direction, and no tracked `.ll` emits one.  All of them are checked, with their
   neighbouring refusals in the same run, by `tests/vector-s1.lean`; the fixture
   `probes/install/ir/json-s1-masks.candidate.ll` uses every one but the `shl`.

   Still absent from the model, and refused by name: vector `alloca` and vector
   `select` (`parseValueInstr`'s `alloca` and `select` arms), a vector `store`
   that is not a mask, a `shufflevector` mask entry at or past `2n` or written
   `undef`, a vector `ashr`, `umin`/`umax`, and a `bitcast` whose total widths
   disagree. A pointer offset is
   modelled: `getelementptr` reads one offset scaled by one of the admitted
   integer element widths (`i1`, `i7`, `i8`, `i16`, `i32`, `i64`, `i128` — the
   widths pinned as having an allocated size equal to the stored size the model
   scales by), with an index
   no wider than 64 bits, and every other shape — a width such as `i24` whose
   allocated size differs, an aggregate, pointer or vector element type, a
   second index, a wider index, the `inrange`/`nuw`/`nusw` modifiers — is
   refused by name (`parseValueInstr`'s `getelementptr`
   branch). The element type is a field of the instruction (`Instr.gep`), so the
   step is `base + off * sizeof(elemTy)` and `i8` is the byte offset this model
   started with. An intrinsic call is **not** refused: the parser
   accepts any callee symbol (`parseValueInstr`'s `call` branch), so a call to
   `@llvm.x86.avx2.pmovmskb`, a gather, a saturating operation or
   `llvm.vector.reduce.*` parses as an opaque `call` whose semantics the model
   does not give. The five symbols the stage-1 kernel calls are the exception:
   `checkIntrinsicShape` validates their arity, operand types and immediate, and
   refuses the neighbouring spellings by name (`tests/vector-s1.lean`). Nothing
   in *this* kernel needs any of them.

state) and the index-emission path will add scalar work and possibly one
