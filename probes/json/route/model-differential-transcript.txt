What the pre-repair run found, and why the model files changed

  The first run of the same script (before the model repair) compared 118 rows
  and reported three corpus divergences.  Each was a model-side defect, not an
  object-side one: the reference parser and the object agree with each other on
  these rows.

  trail-nul.json ("null" followed by a NUL byte)
    The object refused at 4; the model accepted and emitted the null record.
    The literal arm of JsonStage2Body.stage2ScalarValue read the literal's
    length from the token start and compared those bytes, so a token whose
    prefix matched "null" but whose extent was longer passed.  Corrected to
    read the token's own extent, endp - pos, through litCheck: a longer token
    whose prefix matches the literal is refused at the literal's width.

  lit-nul.json ("nul") and lit-tru.json ("tru")
    Verdict and payloads agreed, but the object's refusal offset was 3 and the
    model's was 0.  The same arm wrote the refusal at the token start rather
    than at the first differing position lit_check returns.  Corrected to
    pos + i.

  num-long.json (a 30-digit integer)
    The object accepted with the double's bits; the model aborted with
    "INTERNAL PANIC: Nat.pow exponent is too big" (exit 1).
    JsonStage2Body.numFastEmitted evaluates kernelDecides before numClassOf's
    class gate; for a mantissa at or above 2^64, ElGuardRefine's lz underflows
    and the slice shift exponent (10 + ub) leaves the range Nat.pow accepts.
    Corrected by guarding kernelDecides on the emitted uint64_t argument's
    domain (mantissa < 2^64), with kernelDecides_of_lt recovering the unguarded
    decision inside it.

  Files changed for the repair: LeanLLVM/Refinement/JsonStage2Body.lean
  (litCheck, the literal arm, the kernelDecides guard), and the affected
  proofs in LeanLLVM/Refinement/JsonStage2Helpers.lean and
  LeanLLVM/Refinement/JsonStage2NumFastClass.lean.  The native object, the
  document corpus and the pinned fixture are unchanged.
